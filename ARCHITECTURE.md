# Архитектура — для программиста

Этот документ — вход для человека, который начинает работать с кодом, а
не для продолжения чат-сессии с AI. Если вы ищете журнал методологии
разработки (полная хронология решений, найденных багов, отклонённых
вариантов) — это [`CLAUDE.md`](CLAUDE.md) и [`CHANGELOG.md`](CHANGELOG.md);
они писались как рабочий журнал сессий, не как onboarding, и читать их
целиком для первого знакомства с кодом не нужно. Здесь — только то, что
нужно, чтобы поставить проект локально, понять, как устроен код, и
внести правку.

## Что это

Учебное веб-приложение по санскритской сандхи (71 правило из учебника
Эмено/ван Нотена) — статический сайт без сборки, на vanilla JS
(ES-модули) и Three.js. Правила иллюстрируются двумя способами: 2D-
подсветка на алфавитной панели (почти все 71) и 3D-анимация «слот-
движок» — кубики мела падают, сближаются, превращаются, исчезают
(18 из 71 на сегодня). Живая версия: https://vimo17.github.io/emeneau/.

## Быстрый старт

```bash
npm install                 # ставит three/jsdom/eslint/typescript как dev-зависимости
npm test                    # 236 тестов, ~15 секунд
npx serve docs               # ЛЮБОЙ статический сервер — см. ниже, почему обязательно
# откроется http://localhost:3000 (порт зависит от сервера) — идти в /index.html
```

**Почему нельзя просто открыть `docs/app/sanskrit-sandhi-app.html`
двойным кликом:** приложение использует `<script type="module">` и
importmap — большинство браузеров блокирует загрузку ES-модулей через
`file://` (CORS). Нужен любой статический HTTP-сервер: `npx serve docs`,
`python -m http.server` из папки `docs`, расширение VSCode «Live
Server» — что угодно, лишь бы страница открывалась как `http://`, не
`file://`.

### `docs/app/lib/` — слот-движок

`slot-engine.js` — тонкий barrel-файл (`export * from` на каждый модуль
ниже) — это единственный путь, который импортируют `examples/*.js`,
тестовые страницы и приложение (`import { X } from '../lib/slot-engine.js'`).
Сама реализация разбита по смыслу:

| Файл | Что внутри |
|---|---|
| `slot-engine-core.js` | константы, токенизатор, цвета, easing-функции |
| `slot-engine-cube.js` | фабрика кубика: геометрия/материалы/тень |
| `slot-engine-words.js` | группы слов («вся единица, не одна буква») |
| `slot-engine-steps.js` | шаги (грамматика/правило N), runtime-таймлайн |
| `slot-engine-validate.js` | `validateExampleData` — проверка данных примера перед первым кадром |
| `slot-engine-ops-shared.js` | общие DOM-помощники (кольца/искры/пилюли/волны), нужны нескольким операциям разом |
| `slot-engine-ops-transform.js` | `applyTransform` — буква меняется на месте |
| `slot-engine-ops-elide.js` | `applyElide`/`applyResist` — исчезновение и блокированная попытка исчезновения |
| `slot-engine-ops-influence.js` | `applyInfluence`/`applyApproach` — дальнодействие и физическое сближение |
| `slot-engine-ops-move.js` | `applySplit`/`applyArrive`/`applyMerge`/`applyBud` — создающие/перемещающие кубики |
| `slot-engine-ops-finish.js` | `applySettle`/`applyDim`/`applyStepDim` — завершение и притенение фона |
| `slot-engine-mount.js` | `mountSlotExample` — сцена, кадровый цикл, лента шагов |
| `slot-engine-generate.js` | экспериментальный генератор `ops` из декларативной спецификации — не используется `EXAMPLES[]` приложения, только для сравнения с рукописными данными |
| `slot-engine-types.js` | JSDoc `@typedef` (проверяется `tsc --checkJs`), ноль рантайм-кода |

`chalk-module.js` (рядом, не под `slot-engine-*`) — текстуры/материалы
кубика мела (`paintGlyph`, `buildChalkMaterials`).

### Как работает один пример

Файл `docs/app/examples/ruleN-name-slots.js` экспортирует `data`
(описание: какие буквы падают, какие операции происходят и когда) и
`mount(container)` (вызывает `mountSlotExample(container, data)`). Тот
же файл подключают и тестовая HTML-страница, и основное приложение
(через поле `module` у нужного `EXAMPLES[n]` в `data.js`) — данные не
дублируются.

`data` = `{ initial, steps, ops }`:
- `initial` — какие буквы стоят в каких слотах на старте (10 слотов
  всего, `centeredStart(span)` центрирует раскладку формулой).
- `steps` — границы между «грамматика» и «правило N», с автоматическим
  притенением фона (кто не активен в текущем шаге — притенён).
- `ops` — список операций с таймингом. Каждая — один из типов ниже.

| Операция | Смысл |
|---|---|
| `influence` | Дальнодействие причина→цель (пульс + бегущие волны) |
| `transform` | Буква меняется на месте (глиф+цвет+поворот) — 4 категории: гуна, вриддхи, парная замена внутри варги, ассимиляция под соседа |
| `approach` | Физическое сближение, с паузой на середине пути |
| `split` | Одна буква распадается на две (или полностью заменяется другой) |
| `merge` | Две буквы сливаются в одну |
| `bud` | Отпочкование — истинное удвоение (источник остаётся, клон появляется рядом) |
| `elide` | Буква исчезает без замены |
| `resist` | Попытка исчезновения блокируется другим правилом-исключением |
| `arrive` | Тихий прилёт без слияния |
| `settle` | Финальная волна «всё готово» (автоматическая) |

Полное описание каждого поля — JSDoc в `slot-engine-types.js` (реальная
сигнатура, не пересказ) и построчные комментарии в `slot-engine-ops-*.js`.

## Тесты, линт, CI

```bash
npm test              # node:test, встроенный тестраннер, без Jest/Vitest
npm run lint           # ESLint, только "рекомендованные" правила
npm run check-conventions   # запрещает следы рабочих сессий ("заход N" и т.п.)
npm run typecheck       # tsc --checkJs по JSDoc, только docs/app/lib
npm run audit           # npm audit --audit-level=high
```

Всё это гоняется в CI на каждый push/PR (`.github/workflows/ci.yml`).
Каждый тест в `tests/` привязан к конкретной, реально пойманной
регрессии — подробности и структура тестов в [`tests/README.md`](tests/README.md).

**Чего нет и вряд ли будет:** тестов на само 3D-монтирование
(`mountSlotExample`, реальный рендер в WebGL) — `jsdom` не даёт WebGL-
контекст. Визуальная корректность анимаций (насколько красиво/понятно
выглядит конкретный пример) проверяется человеком в браузере — у автора
предыдущих правок такого доступа не было вообще, только Node.js, так
что перед тем как доверять описанию «визуально подтверждено» в
CLAUDE.md — не считайте это заменой собственной проверки, если меняете
что-то в уже готовом примере.

## Как добавить новое правило (или проверить существующее)

1. Прочитать формулировку правила (`SECTIONS[n].emeno` в `data.js`) и,
   если сомнения — сверить с Whitney (полный текст на Wikisource) и
   найти сутру Панини. Короткая формулировка учебника не всегда полна.
2. Решить механику: какая операция (или комбинация) нужна. Сначала
   смотреть `docs/reference/interaction-registry.md` — там уже
   расписано ожидаемое сопоставление 2D-типа и 3D-механики для всех
   71 правила, включая непостроенные. Использовать существующую
   технику, не изобретать новую без необходимости (см. реестр
   эффектов, CLAUDE.md Часть 4).
3. Прежде чем писать `initial`/`ops` — ответить: где морфологическая
   граница (корень+окончание, слово+слово), и что физически происходит
   при сближении сторон? Часть, участвующая в сандхи, не должна быть
   показана уже собранной с самого начала — событие должно быть
   СЛЕДСТВИЕМ сближения (полная формулировка — CLAUDE.md Часть 2).
4. Написать `docs/app/examples/ruleN-name-slots.js` + тестовую
   страницу `test-slot-engine-ruleN.html`.
5. Прогнать таймлайн реальным кодом (не на бумаге) — простейший способ:
   написать временный `.mjs`-скрипт, который импортирует `applyX` из
   `slot-engine.js` и вызывает на нескольких значениях `elapsed`,
   проверяя позиции/материалы численно. Смотреть, как это уже сделано
   в `tests/applyTransform.test.mjs` и соседних файлах — тот же приём.
6. Открыть тестовую страницу через локальный сервер (см. «Быстрый
   старт») и визуально проверить анимацию в браузере — этот шаг НЕ
   заменяется численной проверкой.
7. Добавить `module` в соответствующий `EXAMPLES[n]` в `data.js`,
   переписать `roleDemo.text` под академический регистр (называть части
   речи и грамматические категории, не только фонетический механизм).
8. Если правило вводит новый санскритский термин на 3D-пилюле
   (`op.label`) — добавить `glossaryTerm` на соответствующий
   `roleDemo.step` и запись в `GLOSSARY` (`data.js`), если её ещё нет.

## Шпаргалка соглашений

- **Один кубик = один звук**, не деванагари-буква и не орфографическая
  буква. Единственное сознательное исключение — маркер паузы `avasāna`
  (данда, `tr:'।'`), см. `suhart-slots.js`.
- Серебро — только гунация, золото — только вриддхи (`TRANSFORM_KIND`,
  `slot-engine-core.js`). Не использовать эти цвета для чего-то ещё.
- Сжатые крайние блоки (для примеров длиннее 10 фонем) — лимит 3 буквы
  на блок (одно согласованное исключение — 4, правило 62).
- Направление отстойника — смысловой сигнал: вверх = превращается
  (`split`), вниз = пропадает без следа (`elide`).
- Полный список зарезервированных значений, цветов, углов поворота —
  CLAUDE.md, Часть 3 («Зарезервированные значения»).

## Где искать больше

- **`CLAUDE.md`** — полная методология и текущее состояние проекта:
  реестр эталонных техник по ситуациям, статус каждого построенного
  правила, список открытых вопросов и незакрытых гэпов. Написан как
  входная точка для AI-чата (первое лицо, обращение «со мной») — не
  ждите human-friendly структуры, но фактическая информация там
  актуальна и обширна.
- **`CHANGELOG.md`** — история разработки по рабочим сессиям, если
  нужно понять, ПОЧЕМУ что-то сделано именно так (какие варианты были
  отвергнуты и почему).
- **`docs/reference/interaction-registry.md`** — сведение 2D-типизации
  правил с 3D-механикой на все 71 правило (единственный такой файл В
  git — остальной лингвистический разбор gitignore'ен, см. ниже).
- **`docs/app/glossary.html`** — санскритские термины (ИАСТ+деванагари),
  которыми названы конкретные сандхи-операции и метаязыковые понятия
  грамматики Панини.

### Чего не будет после клонирования

`docs/reference/*.pdf` (сканы источника) и
`docs/reference/rules-1-71-analysis-consolidated*.md` (обработанный
построчный лингвистический разбор всех 71 правила) исключены из git
намеренно (`.gitignore`) — приватный материал, не для публичного
распространения. `interaction-registry.md` в той же папке — легитимный
общедоступный аналог (механики, не построчный текст источника) — он В
git. Если для работы нужен именно построчный разбор — попросить его у
владельца репозитория напрямую, отдельного публичного источника для
восстановления нет.

## Поддержание документации в актуальном состоянии

Три документа обязаны отражать текущее состояние проекта не реже раза в
сутки работы над ним: этот файл, `CHANGELOG.md` и `CLAUDE.md`. Оба
(`ARCHITECTURE.md` и `CLAUDE.md`) правятся свободно — компрессия,
переписывание устаревшего, удаление лишнего — всё это нормально, ценность
не в полноте истории, а в том, чтобы текущее состояние читалось быстро и
без потери важных деталей (для `CLAUDE.md` — читателем является следующая
AI-сессия, для этого файла — человек). Историю расследований, цитаты
обратной связи и ход поиска багов хранит только `CHANGELOG.md` — в
остальных двух файлах эта детализация не нужна.
