Этот документ — не «шаблон одного примера» (как назывался раньше), а
полная точка входа: если этот чат исчерпается, вставьте этот файл первым

## Часть 1 — Как со мной работать (её прямые требования, не мои привычки)

Каждый пункт ниже — прямое указание, полученное в ходе сессий, не
предположение о хорошем тоне.

1. **Критический подход обязателен.** Не соглашаться ради согласия, не
   останавливаться на первом рабочем варианте — искать слабые места и
   предлагать улучшения без просьбы. Доводить до настоящего завершения,
   не до формального выполнения запроса. Если предложение самого
   пользователя избыточно — прямо возразить и предложить более простой
   путь, не исполнять как есть.
2. **Скорость и минимализм кода — приоритет проекта.** Не добавлять код
   или зависимости без необходимости. Прежде чем писать НОВЫЙ код для
   эффекта/механизма — сначала проверить, нет ли уже готового решения в
   движке (существующий параметр, существующая функция), которое просто
   нужно применить с другими значениями или в зеркальном направлении. Не
   изобретать заново то, что уже решено — цель это унификация всех
   действий, не разрозненные частные решения под каждый пример.
3. **Академический регистр — высшая планка, не «попроще».** Рецензенты —
   лингвисты со степенями. Простой язык пояснений НЕ означает
   примитивизацию: формулировки лингвистически корректны в высшей
   степени, точная терминология (геминация, не «удвоение вдвоём» и т.п.),
   даже в кратких пояснениях к примерам. При этом термин должен быть
   действительно из источника или общепринятой санскритологии, не
   изобретённым — проверять по самому тексту Эменó (PDF — на деле ZIP со
   сканами страниц, без текстового слоя; читать глазами постранично, не
   grep'ать) или по независимым источникам, не полагаться на собственные
   более ранние пересказы.
3а. **`roleDemo.text` — обучает, не пересказывает правило.** Прямое
   требование: суть текстового блока под алфавитом не в том, чтобы
   переформулировать формулу сандхи короче, а в том, чтобы читатель
   понял ЧТО происходит, КАК и ПОЧЕМУ. Обязательно называть части речи и
   грамматические категории задействованных слов/морфем (часть речи,
   род, число, падеж, тип основы, класс глагола и т.п.), не только
   фонетический механизм — короткая фонетическая формула («a перед au
   поглощается») без грамматического контекста НЕ считается достаточной,
   даже если формально точна. Применяется к КАЖДОМУ новому примеру фазы
   автоматической постройки (Часть 6), не только особым случаям.
4. **Пуш — автоматически, если нет открытых вопросов.** Раньше пуш
   откладывался по умолчанию, потому что перенос правок на GitHub был
   ручной работой пользователя (собрать зип, самому вставить команды).
   Это больше не так: пуш выполняется напрямую из этой же сессии
   (git add/commit/push), ручного шага нет — откладывать по старой
   причине незачем. Текущее правило: если по ходу правки не осталось
   вопросов, требующих решения именно пользователя (неоднозначность в
   данных, выбор между вариантами и т.п.), — коммитить и пушить
   самостоятельно, не спрашивая разрешения на каждый пуш отдельно.
   Дожидаться прямого решения нужно только тогда, когда есть что
   реально утвердить — сначала закрыть этот вопрос, потом пушить. Когда
   пуш готовится — по-прежнему сверять с GitHub напрямую (клонировать
   свежую копию, сравнивать файлы), не полагаться на память о том, что
   уже отправлено.
5. **Значимые результаты — фиксировать сухим остатком.** Когда достигнут
   значимый вывод/решение/список открытых пунктов — проактивно предложить
   зафиксировать его (список/таблица, не проза), не оставлять только в
   переписке.
6. **Проверка — численная симуляция, не «на глаз».** Рендера/браузера нет
   вообще — только Node.js. Любое исправление таймлайна, геометрии,
   направления движения проверяется прогоном реального кода (вырезанного
   из самого файла, не переписанного по памяти) на реалистичных данных,
   с явным выводом чисел. Визуальная часть (насколько красиво/читаемо)
   всегда остаётся на подтверждение пользователя — не заявлять «визуально
   готово», когда проверено только численно.
7. **Реестр ведётся проактивно, не постфактум.** Каждое новое
   зарезервированное значение (цвет, число, направление, лимит) — в
   реестр в момент решения, не после того, как ошибка на его отсутствие
   уже произошла на следующем примере.
8. **Порядок фаз: сначала порядок в коде, потом лингвистическая проверка,
   и только потом — новое наполнение.** Прямое указание пользователя: не
   перескакивать на content-задачи (новые примеры, новые правила),
   пока не закончена работа над тем, что уже есть. Две фазы, строго по
   очереди, не параллельно и не вперемешку:
   1) **Программная стандартизация** — код должен пройти проверку
      программистами: тесты, линт, отсутствие мёртвого/устаревшего кода,
      ссылок на несуществующие файлы, следов истории чата в комментариях
      («заход N» и т.п.) — понятен и прозрачен для передачи стороннему
      разработчику без контекста этого чата.
   2) **Академическая проверка исходных данных** — только после того, как
      фаза 1 закрыта: переключиться в режим сверки с источником по
      лингвистике/грамматике санскрита. Проверить ВСЕ термины, связи
      источник/триггер/результат и примеры в данных (`data.js`,
      `EXAMPLES[]`, тексты правил `emeno`) против реального текста Эменó
      (Часть 2а), не полагаться на то, что уже проверялось раньше в
      другой сессии.
   Только когда обе фазы закрыты для конкретного куска работы —
   продолжать наполнение (новые 3D-примеры, новые правила и т.п.).

   **Фаза 2 — ГОТОВА для всех 71 правила (заход 78).** Построчная сверка
   `emeno`-текстов, глоссов и примеров `data.js` с реальным текстом
   источника (`docs/reference/Эмено2.pdf`) — построчно, все 71 правило,
   не выборочно. Найдено и исправлено: 4 подтверждённые ошибки (правило 2 —
   «3 pl.»→«3 sg.», bhavet реально 3 л. ед.ч.; правило 16 — han-
   «гнать»→«убивать», han- стандартно значит «бить, убивать»; правило 18 —
   убран выдуманный корень «snih-», источник даёт только druh-/muh-;
   правило 34 — опечатка «dṛmp-»→«dṛṃh-»), 6 неточных переводов приведены
   к источнику (правила 24, 26, 29, 30, 36, 43 — подробности в сообщении
   коммита `036595a`), 2 примера дополнены/заменены на источниковые
   (правила 25, 37). Заодно, при разборе пояснений `roleDemo.text` ко
   всем 64 примерам: опечатка «висургу»→«висаргу», и в правилах 19/24
   шаг гунирования перед `-sya-` был помечен тегом самого сандхи-правила
   вместо `'грам.'` (путал грамматический факт с сандхи-правилом,
   несогласованно с уже принятой в проекте категоризацией [Грамматика]
   vs [Сандхи N] — видно по тому, что agnayas/āsīt в том же файле
   правильно используют `tag:'грам.'` для аналогичных шагов).

   **Обзор формулировок пояснений — завершён.** Прочитаны все 64
   `roleDemo.text`. Помимо уже перечисленных находок (опечатки, теги
   'грам.', v→y), нашёлся один случай смешения понятий: правило 47
   (`vane + iha`) сравнивало e→a с «гуной наоборот», хотя гуна в проекте
   зарезервирована за морфологической ступенью, зависящей от формы
   слова, а не от соседнего звука (риск путаницы). Переписано по
   формулировке самого правила 47 (в `emeno` сравнения с гуной нет
   вообще — простая фонетическая замена). Остальные 63 пояснения уже на
   хорошем академическом уровне, менять не потребовалось.

## Часть 2 — ГЛАВНЫЙ МЕТОДОЛОГИЧЕСКИЙ ПРИНЦИП

**Суть примера — во ВЗАИМОДЕЙСТВИИ частей, не в готовом целом.** Закреплено
трижды как исправление уже готового плана (āsīt, śādhi дважды) — должно
применяться СРАЗУ на первом черновике, не после замечания.

Если внутри слова есть морфологическая граница (корень+окончание,
приставка+корень, слово+слово) — часть, участвующая в сандхи, НЕЛЬЗЯ
показывать уже собранной с самого начала. Обе стороны границы
падают/существуют РАЗДЕЛЁННЫМИ (зазором), и само событие сандхи —
СЛЕДСТВИЕ их сближения, не декорация поверх уже готового слова.

Практически: перед `initial`/`ops` ответить — «где граница, и что
физически происходит при соприкосновении сторон?» — заложить сближение
как отдельный видимый шаг ДО события сандхи.

**Уточнение (третий заход, тот же принцип глубже): мало развести и
сблизить — нужен ЗАМЕТНЫЙ момент прибытия.** Если сближающаяся сторона
не просто закрывает исходный зазор, а ЕЩЁ И занимает место
исчезающей/меняющейся буквы — это ДВА отрезка пути, не один. Сплошной
путь одной кривой читается как «проехало насквозь», не «подошло →
реакция → въехало». Нужна явная ПАУЗА между «дошло» и «довершило путь» —
реакция происходит ИМЕННО в паузе. В движке: `approach` с
`midDistance`/`midHoldDur`/`leg2Dur`.

**Момент начала реакции требует отдельного сигнала, не только момент
завершения.** Плавная кривая движения имеет нулевую производную в t=0 —
первые кадры визуально неразличимы. Обязательна вспышка+скачок масштаба
РОВНО в момент, когда реакция начинается (см. `elide`, заход 39).

**Геометрия отстойников — точная формула, не подбор.** Отступ от края
слотов до ближнего края отстойника = `CUBE_SIZE/2` (в любую сторону).
`holdOffset.y = FLOOR_Y − CUBE_SIZE/2 − CUBE_SIZE/2`. При CUBE_SIZE=1.1 →
−1.65 для нижнего. Запас у камеры — отдельно, реальной проекционной
математикой (`THREE.Vector3.project`), не на глаз.

**Направление отстойника — смысловой сигнал, не декоративный выбор.**
ВВЕРХ = превращается, что-то продолжается в новой форме (см. `split`).
ВНИЗ = пропадает без следа (см. `elide`).

**Направление любого бокового смещения — проверять числом, что физически
рядом, не полагаться на словесную интуицию.** Дважды пойманная ошибка:
«отступает от X» ошибочно интерпретировалось как движение в фиксированную
сторону без проверки, кто там физически сидит.

## Часть 2а — Источники и обработанный лингвистический анализ

**Обработанный разбор всех 71 правил (114 примеров)** — уже существует,
не нужно делать заново. Файл `rules-1-71-analysis-consolidated (2).md` —
**самая полная и выверенная версия** (13 закрытых открытых вопросов из
16, сверена и с опубликованной книгой 2020г., и с английским оригиналом).
Формат: по каждому шагу **[Тип]** источник→триггер→результат, с W-ссылками
на Уитни. Базовый файл (без номера) и версия `(1)` — более ранние
черновики ТОГО ЖЕ документа (как было раньше с `second-examples-todo.md`)
— можно убрать из project knowledge, чтобы не путать будущие сессии.
Отдельно — `claude/rules-steps-inventory.md`: сводная таблица всех 71
правил по числу шагов и типу операции (ELIDE/MERGE/TRANSFORM/DOUBLE/
DISTANT/INSERT) — дополняет, не дублирует consolidated-файл.

**Английский оригинал** — Emeneau, Van Nooten, *Sanskrit Sandhi and
Exercises*, 2nd rev. ed., University of California Press, 1968. Легитимные
источники (не пиратские):
- WorldCat (библиотечный каталог): https://www.worldcat.org/title/sanskrit-sandhi-and-exercises/oclc/169728
- UC Press (издатель, есть ePub+PDF): https://www.ucpress.edu/books/sanskrit-sandhi-and-exercises-revised-edition
- Google Books (превью/поиск): https://books.google.com/books/about/Sanskrit_Sandhi_and_Exercises.html?id=_9CSzQEACAAJ

Полный текст оригинала в проект не сохраняется (авторское право) —
цитируется только короткими фразами и пересказом, см. дисциплину
цитирования во всём этом документе.

**Если формулировка Эменó не устраивает (слишком лаконична, кажется
неточной или односторонней) — прямое указание пользователя: идти читать
дальше, не оставлять как есть.** Порядок: Уитни (Whitney, уже основной
рабочий справочник проекта, доступен целиком на Wikisource постранично —
`en.wikisource.org/wiki/Sanskrit_Grammar_(Whitney)/Chapter_N`, WebFetch
на весь текст страницы иногда обрезает/суммирует — при необходимости
точной цитаты выкачать raw HTML и вытащить нужный номер параграфа
скриптом, не полагаться на резюме модели), Бюлер (Bühler), Мюллер
(Müller), Фриш/Фрицше (уточнить точную идентичность при следующем
обращении — не проверено, какая именно фамилия), и сам Панини
(Aṣṭādhyāyī, точный номер сутры) — искать НЕ вместо Уитни, а В ДОПОЛНЕНИЕ,
пока формулировка не станет ясной и обоснованной. Пример применения —
правило 1 (a+au→au): формулировка emeno «a поглощается au» заменена на
Whitney §127 (единая таблица гуна/вриддхи-комбинаций) + Pāṇini 6.1.88
vṛddhir eci (технический термин eka-ādeśa, «единая замена» — оба звука
ВМЕСТЕ заменяются одним результатом, не один поглощает другой).

**Реестр взаимодействий и механик на все 71 правило** —
`docs/reference/interaction-registry.md` (заход 79, в git, не путать с
consolidated-файлом выше). Тот файл — лингвистический разбор

правила для 3D-примера сверяться с таблицей там, не с Частью 4 ниже
(та покрывает только 5 уже построенных правил).

## Часть 3 — Архитектура (что построено)

### Файлы
- `docs/app/lib/slot-engine.js` — точка входа, тонкий barrel-файл (заход 62,
  Стадия 5): `export * from` на каждый из модулей ниже, публичный API
  (что импортируют examples/тесты/приложение) не изменился ни на одно имя.
  Не редактировать реализацию здесь — её больше нет в этом файле.
  - `slot-engine-core.js` — константы, токенизатор, цвета, плавность
    (easing-функции), `setOpacity`. Ничего не импортирует.
  - `slot-engine-cube.js` — фабрика кубика (`makeCube`/`regenMats`/
    `updateShadow`), геометрия/материалы/тень. **Заход 64, унификация
    кубика:** геометрия кубика и тени — ОБЩАЯ на все показы (лениво
    строится один раз, `isSharedResource` защищает её от `unmount()`);
    `matsBlank`/`matsReady`/`matsSignal` — ленивые (строятся только при
    первом реальном обращении через `defineMatsSlot`, не все сразу).
    Новый вариант внешности кубика добавлять ТОЛЬКО через `defineMatsSlot`
    (не голым полем) — иначе он не будет уничтожаться при замене и снова
    потечёт память при каждом превращении буквы.
  - `slot-engine-words.js` — группы слов («вся единица, не одна буква»,
    `computeWordGroups`/`resolveSlotRef`).
  - `slot-engine-steps.js` — шаги (грамматика/правило N), runtime-таймлайн.
  - `slot-engine-validate.js` — `validateExampleData` (Стадия 4).
  - `slot-engine-ops.js` — обработчики операций (все `apply*`) и их прямые
    помощники (project/frontAnchor/spawnPulseRing/spawnWave/
    updateGroupFrame/setFacePulse/flyArcPosition) — самый крупный модуль,
    ~1000 строк. Новую `apply*`-функцию добавлять сюда.
  - `slot-engine-mount.js` — `mountSlotExample`, кадровый цикл, лента
    шагов, инъекция стилей.
  - `slot-engine-generate.js` — **ГЕНЕРАТОР данных примера** (заходы
    81, 83, 84, 87) — часть задуманного с самого начала «конструктора»
    (реестр взаимодействий + реестр механик + быстрая сборка, см. Часть
    6). Строит `{initial, steps, ops}` из декларативной спецификации
    (слова + буквы-участники + категория), не вручную. Покрывает ВСЕ 4
    механики, задействованные в 5 уже построенных примерах —
    `buildInfluenceTransformExample`/`buildInfluenceTransformChain`
    (influence+transform, один шаг или цепочка — voicing/place/часть
    grade), `buildApproachMergeExample` (approach+merge), `buildApproach
    ElideExample` (approach+elide), `buildGunaSplitExample` (guṇa+split,
    самая сложная — две механики подряд). Каждый сверен численно с
    реальным эталоном (раскладка побайтово, тайминги — в пределах
    20–250мс постоянного смещения по буферу после падения). Подробности

### Визуальный язык 2D-модели ролей (справка, не 3D-движок)

Источник — без рамки. Триггер — пунктирная обводка. Результат — сплошная
белая обводка. Геометрия: место-ассимиляция (правила 37–40, 69) →
результат берёт столбец от триггера + ряд от источника. Озвончение/
оглушение (31–33) → столбец от источника, только звонкость от триггера.
Гуна/вриддхи → сдвиг источника внутри своего столбца, a/ā — катализатор
без координат. Подсветка всегда по клику на конкретный пример, никогда по
клику на карточку правила целиком.

### Типы операций движка

| Тип | Назначение |

|---|---|
| `influence` | Дальнодействие причина→цель: текстурный пульс на источнике + бегущие волны (`spawnWave`) + рамка группы, если источников >1 |
| `transform` | Буква меняется НА МЕСТЕ (глиф+цвет), 4 категории — см. реестр ниже |
| `approach` | Физическое сближение; поддерживает двухотрезочный путь с паузой (`midDistance`/`midHoldDur`/`leg2Dur`) и непрерывный текстурный пульс на триггере (`holdPulse`) |
| `split` | Одна буква распадается на ДВЕ РАЗНЫЕ (подъём в отстойник вверх, прилёт результатов по дуге) |
| `merge` | Две буквы сливаются в ОДНУ (едущий кубик, вспышка масштаб+emissive в момент контакта) |
| `bud` | Отпочкование — ЗЕРКАЛО `merge` (не вариант `split`): источник остаётся на месте и вспыхивает В МОМЕНТ ПОЯВЛЕНИЯ клона (не в момент контакта, как у merge), клон появляется РОВНО на позиции источника и едет по прямой (`easeOutBackProgress`, НЕ `easeOutBack` — см. ниже) в свой слот. Первый реальный тест гэпа DOUBLE — источник и клон получают ОДИНАКОВЫЙ `toGlyph` (rule61, n→nn), движок не делает для этого ничего особого |
| `elide` | Буква исчезает БЕЗ замены (погружение вниз в отстойник, вспышка в момент начала реакции). Прозрачность держится ПОЛНОЙ на всём погружении+паузе — угасание (и россыпь искр СОБСТВЕННОГО цвета буквы, `spawnSparkleBurst`) сосредоточено в самом конце (`fade`), не размазано по пути — но ТОЛЬКО когда это исчезновение само является содержанием правила. `quiet:true` — тихий вариант (без искр, без ускоренного сжатия, линейное угасание на весь `fadeDur`) для побочных исчезновений внутри чужого главного события (см. Часть 4, критерий) |
| `arrive` | Тихий прилёт буквы без слияния — код готов, ни разу не применён в реальном примере |
| `settle` | Финальная волна «всё готово» — всегда автоматическая |

**РЕАЛЬНЫЙ НАЙДЕННЫЙ БАГ (при разработке `bud`, rule61): `easeOutBack` — не
настоящая 0→1 функция.** Спроектирована специально под связку
`shift*(1-te)` в `applyApproach` (retreat) — там `f(0)=1`, `f(1)=1`, горб
посередине, это ОБРАТНАЯ форма, не обычный 0→1 прогресс с перелётом у
конца. Прямой `lerp(from, to, easeOutBack(t))` (как понадобилось для
`bud`) даёт кубик, ТЕЛЕПОРТИРУЮЩИЙСЯ сразу в цель на t=0 (`easeOutBack(0)
=== 1`, не 0) — пойман сразу тестами (`tests/applyBud.test.mjs`), не в
браузере. Добавлена ОТДЕЛЬНАЯ `easeOutBackProgress` (настоящая формула
Пеннера, РАЗНЫЕ коэффициенты у квадратичного/кубического члена, `f(0)=0`,
`f(1)=1`) — `easeOutBack` НЕ тронута (используется `approach`, риск
регрессии там не нужен).

### Пилюли-подписи эффектов (`spawnLabelPill`, поле `op.label`)

Прямой запрос пользователя: во время события над (или под) местом действия
плавает короткое слово, называющее сам эффект («Гуна», «Вриддхи»,
«Ассимиляция», ...) — не заменяет текст примера, даёт зрителю сразу
считываемый якорь. Тот же DOM-оверлей язык, что и у колец/искр
(`project()` один раз при создании, дальше чистая CSS-анимация,
самоудаление по `setTimeout`) — НЕ отслеживается покадрово (лёгкий боковой
дрейф кубика во время паузы/вращения для читаемости не критичен, та же
логика, что у колец). Две анимации разом на каждой пилюле: «конверт»
видимости (плавно появилась → плавно исчезла, один раз, на всю
длительность события) и непрерывное «дыхание» (лёгкая пульсация
масштабом, фиксированный период 1500мс, зациклена — не зависит от
длительности самого события) — по прямому запросу «подрагивают, дышат,
привлекают внимание». Визуально — та же скруглённая семья, что и у
`.slot-step-chip` внизу, не новый язык.

**Направление — тот же смысловой регистр, что и у направления отстойника
(см. выше в этой же Части 3): `above=true` (над рядом) для
`transform`/`merge`/`split` — «продолжается в новой форме»; `above=false`
(под рядом) для `elide` — «пропадает». Расстояние от ряда — `CUBE_SIZE×1.6`
(«1-2 кубика», по прямому запросу).**

**АЛГОРИТМ РАЗМЕЩЕНИЯ ПИЛЮЛЬ (прямое требование пользователя, закреплено
после rule50 — две пилюли + прилетающий кубик в одном шаге):**
1. **Не пересекаться с объектами.** Не полагаться на подбор числа по
   Евклидовой 3D-дистанции — на rule50 дважды подряд формальный «запас»
   по такой модели визуально всё равно оказывался пересечением (модель
   не учитывает экранную проекцию/ширину самой пилюли). Где возможно —
   структурная гарантия, не приближение: если траектория (`arrivals`,
   `holdOffset`) МОНОТОННА по одной из осей (проверяется численно, как
   `flyArcPosition`/`easeInOutCubic` реально ведут себя на всём t∈[0,1]),
   размещать пилюлю по ДРУГУЮ сторону этой границы (`labelX`) — тогда
   пересечение исключено по построению, а не численно маловероятно.
2. **Несколько пилюль рядом — на одной прямой.** Если в одном шаге у
   двух и более операций есть `label`, их `labelY` (и, если применимо,
   ось выравнивания) должны совпадать — иначе события читаются как два
   разных, а не одна связная реакция (см. `SplitOp.labelY`/`labelX`,
   `TransformOp.labelY` в `slot-engine-types.js`).
3. Оба поля (`labelX`/`labelY`) — необязательные per-op переопределения,
   НЕ менять дефолт `spawnLabelPill` (`CUBE_SIZE×1.6`, x по `above`) —
   он безопасен для всех остальных, уже подтверждённых примеров
   (agnayas, rule42, rule55, rule70/71). Трогать дефолт для одного
   примера — риск тихой регрессии в другом (см. НАЙДЕННЫЙ БАГ выше,
   rule50/agnayas).

Поле `op.label` — необязательное, добавляется на КОНКРЕТНЫЙ экземпляр
операции в данных примера, не выводится автоматически из `signal`/
`TRANSFORM_KIND` — движок не пытается угадывать словесную категорию
(`vargaPair`, например, может означать и озвончение, и оглушение, и
назализацию в зависимости от конкретных букв). Момент появления — начало
РЕАЛЬНОГО действия (конец anticipateDur у transform/split, `op.start` у
merge/elide), не раньше паузы-осознания. Длительность — вся видимая жизнь
события (оборот+пауза-фиксация у transform; путь мувера+спад вспышки у
merge; подъём+ожидание+сравнение+угасание у split; rise+hold+fade у
elide — включая `quiet`, тихий elide тоже получает подпись, просто без
искр/сжатия).

**Словарь уже применённых подписей — реестр, не изобретать заново
термин на каждый новый пример.** ПЕРЕВЕДЕНО НА ИАСТ, всегда строчными
(прямое требование пользователя, живая проверка rule50 — прежние
кириллические подписи держали непоследовательный регистр между
примерами; академический регистр требует настоящих санскритских
терминов, не русских калек, см. Часть 1 п.3):

| Механика | Подпись | Где применено |

6, старые прототипы `docs/effects/rule-samprasarana-*.html`), возможные

**Термины, остающиеся НЕ решены — требуют проверки по источнику, не
гадать:**
- «ассимиляция» (кириллица, временно) — taddhiraṇyam шаг1, h→dh,
  место-ассимиляция вне варги.
- «слияние» (кириллица, временно) — rule 50, -as→o, P6.1.113 — НЕ
  savarṇadīrgha, та формула строго для одинаковых гласных.
- «геминация» (кириллица, временно) — rule 61, n→nn, истинное удвоение.
- **РЕШЕНО. `lopa` у rule1 — сомнение пользователя было верным, термин
  ДЕЙСТВИТЕЛЬНО не подходил.** Проверено (Pāṇini 6.1.84/6.1.87/6.1.88,
  sanskritdictionary.com — см. таблицу выше): `lopa` строго означает
  замену на ноль (P. 1.1.60 adarśanaṃ lopaḥ), а в rule1 результат ЕСТЬ
  (au) — просто зрительно совпадает с одним из исходных звуков. Верный
  термин — `ekādeśa` («единая замена», P. 6.1.84, адхикара на весь блок
  6.1.72–6.1.111, включая и 6.1.87 (rule2, ād guṇaḥ), и 6.1.88 (rule1,
  vṛddhir eci)). Подпись добавлена в `rule1-devau-slots.js` (на `elide`
  звука a — тот, что физически исчезает с экрана, хотя грамматически
  «исчезновением» это не является).

**РЕАЛЬНЫЙ НАЙДЕННЫЙ БАГ (rule15, по скриншоту пользователя): пилюля

раскачивания разное по знаку в разных примерах, единого безопасного
сдвига там нет).

**РЕАЛЬНЫЙ НАЙДЕННЫЙ БАГ (та же сессия): пилюля `transform` держалась
ещё `holdDur` (700мс) ПОСЛЕ того, как кубик уже вернул истинный цвет.**
`cube.mesh.material = cube.matsMain` (возврат истинного цвета) происходит
РОВНО в момент посадки (`t>=1`, `applyTransform`) — `holdDur` идёт уже
ПОСЛЕ этого, чистая пауза-фиксация готового результата, к сигнальному
цвету (silver/gold) отношения не имеет. Пилюля же была рассчитана на
`dur+holdDur`, то есть надпись «Гуна»/«Вриддхи» видимо переживала момент,
который она называет. Исправлено — длительность строго `dur`. Проверено
численно на guṇa и vṛddhi (реальный `applyTransform`): к моменту
исчезновения пилюли материал уже 100% `matsMain`. 1 новый тест.

**РЕАЛЬНЫЙ НАЙДЕННЫЙ БАГ (та же сессия, `sanskrit-sandhi-app.html`):
вступительный экран мелькал на долю секунды даже у тех, кто его уже
видел.** `#intro-overlay` в CSS был видим ПО УМОЛЧАНИЮ (`display:flex`),
скрывался только отложенным (`type="module"`) скриптом ПОСЛЕ проверки
`localStorage` — браузер успевал покрасить страницу с видимым оверлеем до
того, как скрипт его прятал. Исправлено — база `display:none`, класс
`.is-open` добавляется JS ТОЛЬКО для первого визита (не наоборот,
«показан всегда — скрыт при необходимости»).

- **Серебро/золото (`matsSignal`/`matsGold`, `op.signal:'silver'|'gold'|'blank'`)**
  — серебро ТОЛЬКО гунация, золото ТОЛЬКО вриддхи (решено пользователем
  напрямую, отдельные, не путать друг с другом). Не декоративное «что-то
  происходит» — конкретный сигнал «идёт огласовка (гуна/вриддхи)».
  `TRANSFORM_KIND.vrddhi` = `{spinTurns:2, signal:'gold'}` реализован.
  **Материал — металлический, не плоская заливка** (`buildMetallicMaterials`
  в `chalk-module.js`, вызывается напрямую из `matsSignal`/`matsGold` в
  `slot-engine-cube.js`): многостоповые градиенты по роли грани (верх/
  блик-полоса/тень, `METALLIC_ROLE_BY_FACE`) + ambient occlusion, палитра
  портирована из референса пользователя (готовый SVG/React-компонент
  изометрического куба, силуэт не переносился — только hex-стопы
  градиентов). Это ручная 2D-имитация, **не настоящее отражение** —
  единственная попытка честного `envMap` (`THREE.PMREMGenerator`,
  `metalness`) не довелась до убедительного результата без возможности
  видеть рендер вживую (доводка шла по скриншотам, раунд за раундом, и не
  сошлась). **Открытый пункт на будущее: вернуться к настоящему отражению
  отдельным заходом**, когда появится способ смотреть на живой рендер
  (интерактивная сессия/скрин-шеринг), не только по присланным
  скриншотам — само направление (envMap) технически рабочее, просто
  требует другого канала обратной связи, не блок на архитектуре.
- **`GROUP_COLOR`** — нейтральный, структурные события (вспышки merge/elide,
  рамка группы, сжатые многобуквенные блоки).
- **Категории `transform`** (угол поворота И цвет промежуточной фазы —
  ОДНА система, не два разных факта). **С заходом 54 — именованные
  пресеты в коде** (`export const TRANSFORM_KIND` в `slot-engine.js`),
  не только описание здесь: `{ type:'transform', ..., ...TRANSFORM_KIND.vargaPair }`
  вместо голых чисел вручную в каждом примере — снижает риск ошибки
  (заход 46: `spinTurns` был перепутан именно из-за ручного повторения).
  - Гунация → `spinTurns:1` (360°) + `signal:'silver'` (дефолт движка —
    в `TRANSFORM_KIND` НЕ включена, передавать нечего, agnayas как был
    без явных параметров, так и остался).
  - Вриддхи → `TRANSFORM_KIND.vrddhi` = `spinTurns:2` (720°) +
    `signal:'gold'` — реализовано в `TRANSFORM_KIND` и в движке
    (`matsGold`, `signalMats` в `applyTransform`).
  - **Идея на будущее, пока НЕ реализована:** то же различие
    серебро/золото — не только для сигнального цвета САМОЙ буквы при
    `transform`, но и для рамки-подчёркивания ГРУППЫ-причины
    (`GROUP_COLOR`/`updateGroupFrame`, сейчас один нейтральный цвет на
    все случаи) — серебряная рамка под группой, вызывающей гунацию,
    золотая — под группой, вызывающей вриддхи. Даёт зрителю дополнительный
    сигнал ДО того, как начнётся сам оборот буквы, какая огласовка
    предстоит. Реализовать вместе с первым реальным примером вриддхи, не
    заранее вслепую (тот же принцип, что и у `signal:'gold'` самого
    `transform`).
  - Парная замена внутри варги (k↔g, глухая↔звонкая, придых↔непридых,
    любая↔назальная) → `TRANSFORM_KIND.vargaPair` = `spinTurns:0.5`
    (**180°, противолежащая грань** — геометрически материализованная
    «пара») + `signal:'blank'`.
  - Общая ассимиляция ПОД СОСЕДА (буква вне всех варг — h/ṃ/ḥ — целиком
    меняет место образования) → `TRANSFORM_KIND.assimToNeighbor` =
    `spinTurns:1` (**360°, не 180°** — нет «противолежащей грани», буква
    не парная сама по себе) + `signal:'blank'`.
- **Тяжесть/скорость вращения `transform` — ОБРАТНО пропорциональна углу
  поворота, не общая формула spinTurns×MS_PER_360 везде одинаково.**
  Прямое решение пользователя (заход 82): чем МЕНЬШЕ угол поворота, тем
  ЗАМЕТНЕЕ должно быть медленным и тяжёлым вращение — небольшой поворот
  сам по себе даёт мало визуального сигнала, нужна медленная, весомая
  подача, чтобы факт превращения осознавался (обучающее приложение, не
  просто красивая анимация). Уже реализовано для `vargaPair` (180°) —
  1800мс, НЕ `0.5×MS_PER_360` (700мс) — портировано из эталона
  `docs/effects/rule-assimilation-varga-t-d.html`, см.
  `landsOnOppositeFace` в `applyTransform` (`slot-engine-ops.js`).
  **РЕШЕНО (заход 98). `MS_PER_360` = 2000 (было 1400)** — прямое
  замечание пользователя после живой проверки agnayas: гунация читалась
  слишком быстро, «нельзя быстро понять, что происходит». Одна общая
  константа на гунацию И вриддхи (не отдельная скорость для 720°) —
  вриддхи автоматически получает ту же угловую скорость, вдвое дольше по
  времени (2×2000=4000мс), тем же принципом, каким прямо попросил
  пользователь. Все ПОСЛЕДУЮЩИЕ (после transform.start) числа в
  `rule3-agnayas-slots.js` сдвинуты на +600мс (разница длительности одного
  оборота) — иначе следующий шаг стартовал бы всего через 100мс после
  реального приземления вращения (было 700мс запаса) — тот же ритм,
  просто позже. **taddhiraṇyam/vāk asti — НЕ пересчитаны** (их transform-
  категории — vargaPair/assimToNeighbor с ОТДЕЛЬНЫМИ фиксированными
  длительностями, не завязанными на MS_PER_360 напрямую тем же образом,
  кроме assimToNeighbor — h→dh в taddhiraṇyam использует spinTurns:1,
  формулу-таки заденет; открытый пункт — сверить при следующей визуальной
  проверке этого примера).
- **Один кубик = одна фонема** (принцип с самого начала проекта, IAST
  сегментален по построению). Многобуквенный `tr` — ТОЛЬКО для сжатых
  крайних блоков инертного контекста (см. реестр), различать от
  однофонемных многобуквенных записей (придыхательные, дифтонги ai/au) по
  точному списку `MULTI_CHAR_PHONEMES`, не по длине строки.
- **Один цвет для всего не-главного.** Цвет чипа шага определяется ТОЛЬКО
  тем, главный ли шаг (`primary:true`), не его `kind`. Всё не главное
  (грамматика И вспомогательное правило в цепочке) — один и тот же
  стандартизированный охровый (`is-grammar`, `#CDA84E`), не новый цвет.
- **Сжатые крайние блоки — лимит ЖЁСТКИЙ, ровно 3 буквы.** Единственное
  согласованное исключение — 4 буквы, только для одного случая (правило
  62, «yati»), не прецедент для произвольного превышения.
- **Направление бокового раскачивания `transform`** (`op.clearance`,
  дефолт +0.35, вправо) — проверять для КАЖДОГО нового `transform`, кто
  сосед с какой стороны; раскачивание должно идти к пустому месту, не к
  занятому. Отрицательное значение — то же самое поле, зеркально.

### Центрирование раскладки и адаптивный FOV камеры (заходы 89–90)

Найдено и закрыто по итогам живой визуальной проверки пользователем всех
пяти интегрированных примеров: rule15 обрезался по левому краю сильнее,
чем более длинный taddhiraṇyam, хотя короче — потому что был не
центрирован (см. Часть 5.2). Прогон реальной камеры движка через
`.project()` (не на глаз) показал, что горизонтальный запас камеры
никогда не проверялся вообще (в отличие от вертикального — см. комментарий
у `camera.lookAt` в `slot-engine-mount.js`), и что старые (до общего
движка) `rule3-agnayas.js`/`rule71-vak-asti.js` уже решали ровно эту
задачу — решение было утеряно при консолидации в общий движок, не
отсутствовало никогда как идея.

**Центрирование — не подбор на глаз, одна формула на все примеры.**
`centeredStart(span)` (`slot-engine-core.js`) — `Math.floor((N_SLOTS -
span) / 2)`, единственный источник этой арифметики: `centerSlots`
(авторская утилита для одного слова) и `layoutWords` в
`slot-engine-generate.js` (генератор, несколько слов + зазоры) теперь оба
вызывают её, не дублируют формулу каждый по-своему. rule15 пересчитан
этой формулой (2..7, было 0,1,2,4,5 — след диагностики прозрачности,
заход 80, давно закрытой, заход 86). rule3/7/70/71 не трогались — уже
центрированы формулой либо близко к ней (offset ≤0.5 слота из-за чётности
span, неизбежность самой арифметики, не ошибка).

**Масштаб — НЕ единая уменьшенная константа, а адаптивный FOV, портированный
из старых файлов, не изобретённый заново.** Пользователь прямо
сформулировал требование, в два приёма: сперва — кубик должен быть ОДНОГО
размера во всех примерах (иначе взгляд каждый раз «привыкает заново» — это
мешает запоминанию, не только эстетика), и весь пример должен
масштабироваться как единое целое при сжатии окна (как раньше делал именно
рукописный `rule71-vak-asti.js`). После первой реализации — живая проверка
в браузере (rule3 крупнее rule70 на одном и том же окне) уточнила: «один
размер» должен выполняться ВСЕГДА, не только на широком окне, и эталон —
максимально заполненный случай (rule70), а не «каждый пример настолько
крупный, насколько ему самому позволяет его собственная ширина». Первая
версия (`hw` считался от занятого диапазона КОНКРЕТНОГО примера) не
удовлетворяла этому — короткие примеры оставались крупнее длинных до тех
пор, пока узость окна не заставляла именно ИХ ужиматься. Исправлено сразу
той же сессией:
- `HALF_WORLD_H` (`slot-engine-core.js`, =2.3) — ОБЩАЯ константа для всех
  примеров без исключения, дословно перенесена из старых файлов.
- `HALF_WORLD_W_MAX` = `halfWorldW(0, N_SLOTS-1)` — ТОЖЕ общая константа,
  не своя под каждый пример: половина мирового габарита самого широкого
  теоретически возможного случая (сейчас это ровно taddhiraṇyam, весь
  стенд 0..9). `halfWorldW(minSlot, maxSlot, margin)` как отдельная утилита
  осталась (честный максимум `|левый край|`/`|правый край|` от x=0, не
  `totalSpan/2` — та формула у старых файлов предполагала центрированную
  раскладку и молча занижала бы отступ у смещённой), но `mountSlotExample`
  теперь не вызывает её для текущего примера — всегда передаёт в
  `computeFitFov` одну и ту же `HALF_WORLD_W_MAX`, независимо от того,
  какой пример показан.
- `computeFitFov(aspect, camZ, hw, baseFov)` — `camera.fov = max(baseFov,
  fovForHeight, fovForWidth)`, пересчитывается в `resize()`
  (`slot-engine-mount.js`) на каждый `ResizeObserver`. Поскольку `hw`
  теперь всегда одна и та же константа, результат тоже гарантированно
  одинаков у всех примеров при любом aspect — не только на широком окне.
- Проверено численно (`tests/cameraFit.test.mjs`, 12 тестов) и живым
  прогоном реальных данных всех 5 примеров на 4 aspect ratio: FOV идентичен
  у всех пяти в каждой точке (32° при aspect≥3, растёт согласованно при
  сужении) — визуальная разница между примерами больше не зависит от того,
  какой из них сейчас на экране, только от ширины окна.

### Правки по живой проверке rule42/agnayas (заход 98)

Четыре отдельные находки одной сессии, все — прямые замечания пользователя
по экрану, не гипотезы.

**Момент смены буквы при вращении — три версии за одну сессию, финальная
задана пользователем ПОЗИЦИОННО, не углом на глаз.** Первая версия
(t≥0.15, доля времени) давала для гунации ~139° (грань уже скрыта,
работало), но для вриддхи (spinTurns:2) ТУ ЖЕ долю 0.15 от вдвое
большего пути — ~278°, с заметной паузой перед повторным появлением
грани. Вторая версия (фиксированный угол, 90°→130°) боролась с тем же
симптомом другим способом — тоже не то: при spinTurns:2 обе стороны
кубика перекрашиваются в НОВЫЙ глиф сразу после подмены, а дальше кубик
делает ещё почти два оборота — значит новая буква успевает промелькнуть
на каждом развороте (было замечено численно: 4 раза за один transform),
это читалось как «мельтешение уже готового ответа», а не единый момент
реакции. Пользователь задала точную ПОЗИЦИОННУЮ схему (шаг 90°, позиция
N = (N−1)×90°): позиции 1–2 — старая буква; **один оборот (гунация)** —
на позиции 3 (180°, «зад» первого оборота) старая буква ЗАМЕНЯЕТСЯ НОВОЙ
в тот же момент, без разрыва; **два оборота (вриддхи)** — на позиции 3
старая буква ГАСНЕТ В ПУСТОТУ (грань без буквы, но в сигнальном золоте/
серебре), и остаётся пустой вплоть до позиции 7 (540°, «зад» уже ВТОРОГО
оборота) — только там наносится результат. Формула: `disappearDeg=180`
(всегда), `revealDeg=(spinTurns−1)×360+180` (совпадает с disappearDeg
при одном обороте — разрыва нет; даёт 540 при двух — целый оборот
ожидания). Реализовано как два независимых порога (`op._disappeared`/
`op._revealed`) в `applyTransform` (`slot-engine-ops.js`) — «пустая»
грань на время ожидания строится через `buildMetallicMaterials(variant,
seed, null)` (без глифа, glyph=null у `paintGlyph` просто ничего не
рисует), временный набор уничтожается сразу после reveal. Проверено
численно на agnayas (1 оборот) и rule42 (2 оборота) — точно совпадает с
заданными позициями.

**НАЙДЕННЫЙ И ИСПРАВЛЕННЫЙ БАГ (тот же заход, доп.): позиционная схема
выше была реализована ВЕРНО, но пользователь всё равно видела «лишние»
появления буквы — причина оказалась не в порогах, а в том, что
`buildMetallicMaterials` красила букву на ОБЕИХ торцевых гранях (idx4 И
idx5), как и `buildChalkMaterials`.** Этот приём оправдан для
`landsOnOppositeFace` (vargaPair, 180° — к зрителю в конце ЗАКОНОМЕРНО
возвращается именно ПРОТИВОЛЕЖАЩАЯ грань), но для гунации/вриддхи (полный
оборот, к зрителю всегда возвращается ИСХОДНАЯ грань) задняя грань,
получив ту же буку, становится видна В СВОИХ СОБСТВЕННЫХ окнах поворота
(90–270°/450–630° при двух оборотах, реальная геометрия граней через
кватернион — не предположение) — показывая то старую, то (после подмены)
уже новую букву ВТОРОЙ раз, помимо фасада. Пользователь прямо
сформулировала: буква — ТОЛЬКО на фасаде (первой грани), задняя всегда
остаётся пустым металлом. Исправлено в `buildMetallicMaterials`
(`chalk-module.js`) — глиф красится только на `idx===4`, никогда на
`idx===5`; сама позиционная схема (disappearDeg/revealDeg) не изменилась
— «пропадание» на позиции 3 теперь просто гасит фасад, задняя грань и
так всегда была пустой.

**Золотая россыпь искр во время вращения вриддхи** — прямой запрос
пользователя, `spawnSparkleBurst` (`slot-engine-ops.js`) — несколько
мелких золотых точек разлетаются от передней грани и гаснут, тот же
DOM-оверлей-язык, что и кольца/волны (`project()`, CSS-анимация на
custom property, `setTimeout`-самоудаление), просто новая форма. Включена
автоматически при `op.signal === 'gold'` внутри активной фазы вращения —
в данных примера ничего дополнительно указывать не нужно. Только золото —
серебро/гунация без искр, различие намеренное.

**Высота старта падения — была `y=6` (плюс разброс до `y=8`), проверено
реальной проекционной математикой камеры (`THREE.Vector3.project`):
проецируется в NDC y≈2.25 при обычном (широком) окне — больше чем вдвое
выше видимого края кадра (кадр кончается на NDC y=1, видимый верх сцены
— около `y=2.9`).** Кубик визуально появлялся, уже пролетев больше
половины пути — прямая формулировка пользователя («буква выпадает
слишком близко к тексту», хотя место для анимации есть) была правильной:
место действительно оставалось неиспользованным, просто выше камеры.
Исправлено — `FALL_START_Y=3.6` (чуть выше видимого края, небольшой
запас на «влетание», не глубоко за кадром), см. `slot-engine-mount.js`.
Видимая часть падения выросла с ~половины прежнего пути до почти всей
дистанции.

**РЕАЛЬНЫЙ НАЙДЕННЫЙ БАГ (интеграция rule50, живая проверка в самом
приложении, не на тестовом полигоне): `FALL_START_Y=3.6` было
откалибровано только для «обычного (широкого) окна» (aspect≥2, где
`computeFitFov` держится near-`baseFov`).** Реальная панель `.eff-stage`
в приложении часто УЖЕ этого (aspect~1.5-1.8 — растёт `camera.fov` через
`fovForWidth`, а не только `fovForHeight`) — на такой пропорции 3.6
проецируется ВНУТРЬ кадра (проверено численно: pixelY от +24 до +76 на
реалистичных размерах панели), верхняя строка кубиков становилась видна.
Исправлено — `FALL_START_Y=5.0`, остаётся скрытым на всём проверенном
диапазоне (900×440 узкий тестовый полигон .. 1150×620 заметно более
квадратная панель). **Затрагивает ВСЕ 8 интегрированных примеров**
(общая константа, не только rule50) — эффект чисто позиционный (старт
чуть дальше от кадра), `fallDur` не меняется, длительность падения та
же, только пройденная дистанция немного больше.

**MS_PER_360 замедлен (1400→2000мс/оборот) — прямое замечание
пользователя после проверки agnayas** («слишком быстрая, нельзя быстро
понять что происходит»). Одна общая константа на гунацию и вриддхи (см.
выше, «Тяжесть/скорость вращения»); подробности каскадного пересчёта
`rule3-agnayas-slots.js` — там же.

**Отстойник `elide` (буква пропадает вниз) — ДВЕ правки за сессию, первая
была с ошибкой.** По прямому запросу пользователя пересчитан
«симметрично» отстойнику `split`: немного сбоку, зазор МИНИМУМ 1 кубик
вниз. Был `holdOffset: {x:-0.2, y:-1.65, z:-0.4}` — боковой сдвиг едва
читался. **Первая правка** (`{x:-0.45, y:-1.1, z:-0.4}`) содержала
реальную ошибку — перепутан ВЕРХНИЙ КРАЙ отстойника с его ЦЕНТРОМ: y=-1.1
оказался верхним краем кубика в отстойнике, а не центром, из-за чего
зазора между низом ряда и отстойником не было вообще (кубик стоял
впритык) — найдено пользователем по скриншоту. **Исправлено на
`{x:-0.45, y:-2.2, z:-0.4}`** — FLOOR_Y(-0.55) минус зазор (минимум
CUBE_SIZE=1.1, не CUBE_SIZE/2) даёт верхний край отстойника (-1.65),
минус ещё CUBE_SIZE/2 (половина кубика) — его центр (-2.2). Видимого пола
в сцене нет — перекрыть нечем, но запас камеры на этой глубине уже
заметно меньше прежнего (NDC y=−0.817, край кадра −1.0) — глубже без
повторной проверки не отодвигать.

**rule42 (tatraiti) пересчитан дважды в одной сессии** — сначала
центрирование (взвешенное решение: раскладка сдвинута на +1 слот, чтобы
центрировался ИТОГОВЫЙ 7-буквенный результат «tatraiti», не временная
9-слотовая раскладка ДО событий — финальное состояние держит внимание
зрителя дольше всего, это на нём и стоит фокусировать центр), затем
тайминги под новый MS_PER_360 (elide/approach/end пересчитаны от новой
фактической точки приземления transform, 11040 вместо 9840). Проверено
численно — центр итогового слова сдвинут с −1.8 до −0.6 (тот же остаточный
сдвиг, что у agnayas/vāk asti — предел чётности слотов, не ошибка), все
семь букв стоят вплотную без наложений.

### Улучшение эффекта elide + НАЙДЕННЫЙ И ИСПРАВЛЕННЫЙ БАГ (правило 55)

По прямому запросу пользователя («сделай исчезновение более выраженным»)
`applyElide` переработан: прозрачность держится ПОЛНОЙ на всём погружении
и паузе (было — таяла уже по дороге вниз, до 0.5 к концу подъёма, что
смазывало сам момент падения), угасание сосредоточено целиком в финальной
фазе (`fade`) — резкое, не размазанное. В момент начала fade добавлена
россыпь искр (`spawnSparkleBurst`, тот же приём, что и золотые искры
вриддхи, но нейтральным `GROUP_RGB` — золото остаётся строго за вриддхи).
`spawnSparkleBurst` заодно параметризован по цвету (4-й необязательный
аргумент `rgbStr`, тот же приём, что и у `spawnPulseRing`) — раньше цвет
был зашит в CSS намеренно («искры только у золота»), теперь переопределяем
инлайн для elide, вриддхи не меняется.

**РЕАЛЬНЫЙ НАЙДЕННЫЙ БАГ, обнаруженный при проверке (не гипотетический):**
`applyStepDim` выполняется КАЖДЫЙ кадр ПОСЛЕ `applyElide` в общем цикле
рендера (см. `renderAtElapsed`, `slot-engine-mount.js`) — если исчезающий
слот входит в `activeSlots` текущего шага (а он ВСЕГДА входит — s/a в
śādhi/rule42/rule55 являются заявленными участниками события), `applyStepDim`
каждый кадр принудительно возвращал его прозрачность к 1, полностью
перебивая кривую elide. Это означало, что угасание `elide` НИКОГДА не было
видимо ни в одном из трёх уже построенных примеров (śādhi, rule42, rule55)
— на экране буква держалась полностью непрозрачной весь путь, потом резко
«щёлкала» в невидимость в момент `cube.mesh.visible=false`, без плавного
угасания вообще. Найдено экспериментально (числовым прогоном `applyElide`
+`applyStepDim` в реальной последовательности вызовов) при попытке
реализовать «прозрачность держится полной» для rule55 — оказалось, что
это уже ПРОИСХОДИЛО случайно, по другой (ошибочной) причине.
**Исправлено** — `applyStepDim` теперь пропускает любой слот, который
является целью (`at`) активного (уже начавшегося, ещё не завершённого)
`elide`-события, определяется без дополнительных флагов: слот всё ещё
существует в `cubes` (elide удаляет его сам по завершении) И его elide уже
начался (`op.start <= elapsed`). **Затрагивает уже интегрированный и ранее
подтверждённый пример śādhi (`EXAMPLES[15]`)** — требует повторной
визуальной проверки, момент исчезновения S теперь выглядит иначе (см.
Часть 5.2, строка 15). 4 новых теста (`tests/applyElide.test.mjs`,
`tests/applyStepDim.test.mjs`) — оба факта (кривая прозрачности, пропуск
активного elide в applyStepDim) закреплены как регрессии, не абстрактно.

**Доп. правка той же сессии, по прямой обратной связи после просмотра**
(«на порядок больше брызг разного размера во все стороны, сейчас
ощущение трёх капелек» — касается ОБОИХ мест: elide И вриддхи, одна и та
же функция): `spawnSparkleBurst` переработан — count по умолчанию 4→16 (не
дублируется отдельным числом на каждый вызов — общий дефолт, elide теперь
просто не передаёт count вообще), дистанция разлёта увеличена (было
16–44px, стало 20–80px), у КАЖДОЙ искры отдельно случайный размер (3–12px,
было — одна и та же величина 5px у всех) и свечение (box-shadow),
масштабированное под этот размер, ставится ИНЛАЙН всегда (не только при
переопределении цвета — иначе крупные золотые искры вриддхи остались бы с
тем же узким статичным ореолом, что и мелкие). CSS `.slot-sparkle` теперь
держит только структурные свойства (position/border-radius/animation) —
размер/цвет/свечение больше не статика. Затрагивает и уже построенный (но
пока не интегрированный) rule 42 — его же спарклы вриддхи станут заметно
ярче/крупнее при следующей визуальной проверке, без каких-либо изменений
в данных самого примера.

**ТРЕТЬЯ правка той же сессии — структурная, не только количество.** По
прямой формулировке пользователя: «кратно больше, в 10-20 раз, разного
размера — но ГЛАВНОЕ, чтобы кубик РАССЫПАЛСЯ, а не стрелял из точки и
потом [отдельно] исчезал». Два независимых исправления:
1. **count 16→200** — и, что важнее самого числа, у КАЖДОЙ искры теперь
   СВОЯ случайная стартовая точка, разбросанная по всей видимой площади
   кубика (раньше все стартовали из одной общей точки — `frontAnchor` —
   и только разлетались в стороны, что и читалось как «выстрел», не
   «распад»). Ширина разброса переведена из мировых единиц в пиксели
   через РЕАЛЬНУЮ проекцию камеры (вторая опорная точка на +1 мировую
   единицу, та же техника, что и у `project()` везде в движке), не
   константа — иначе при разных FOV/масштабах экрана разброс был бы то
   теснее, то шире самого кубика.
2. **Синхронизация исчезновения самого кубика с темпом искр.** Раньше
   `elide`'s собственное угасание (прозрачность 1→0) было растянуто на
   ВЕСЬ `fadeDur` (1100мс), а недолгие искры (~450–850мс) успевали
   разлететься и погаснуть заметно раньше — визуально ДВА разъединённых
   события («искры стрельнули, потом [позже] кубик отдельно истаял»), не
   одно. Добавлена ускоренная визуальная кривая (`visT = t×1.8`) для
   ОБЕИХ величин разом — прозрачности И масштаба (масштаб раньше в fade
   вообще не трогался, сжимается до `0.12` синхронно с угасанием) — кубик
   реально сжимается и тает НА ТОМ ЖЕ темпе, что и искры, читается как
   один распад. `fadeDur` как ОБЩАЯ длительность не менялась (важно —
   `step.end`/auto-settle у уже готовых śādhi/rule42/rule55 остаются
   валидными без пересчёта, просто с чуть большим запасом буфера, чем
   строго необходимо) — ускорена только видимая кривая ВНУТРИ неё, кубик
   держится невидимым остаток fadeDur перед фактическим удалением.
   Побочная правка: скачок масштаба от удара (op.start, `_impactAt`)
   теперь ограничен `elapsed < fadeStart` — иначе этот блок (идёт ПОСЛЕ
   fade-ветки в коде) каждый кадр перезаписывал бы новое сжатие обратно
   в 1. 2 новых теста (сжатие+угасание реально быстрее fadeDur, кубик не
   «оживает» между визуальным исчезновением и фактическим удалением).

**ЧЕТВЁРТАЯ правка той же сессии — по итогам живой проверки, три отдельных
уточнения.** «Работает, но»:
1. **Цвет искр elide — СОБСТВЕННЫЙ цвет буквы, не нейтральный.** Было
   `GROUP_RGB` (тот же нейтральный тон, что и у групповых вспышек merge) —
   заменено на `ringColorFrom(colorFor(cube.tr))`, ту же формулу, что уже
   используют кольца `influence` («кольцо читается как СОБСТВЕННОЕ свечение
   кубика, не безликий сигнал»). Прямая формулировка: «как будто кубик
   рассыпается на части» — осколки должны быть цвета самой буквы, не
   постороннего нейтрального тона.
2. **Финальное кольцо-вспышка ПОСЛЕ угасания убрано.** `spawnPulseRing`
   сразу перед `delete cubes[op.at]` (в момент, когда кубик УЖЕ невидим)
   был лишним повтором сигнала — россыпь искр уже полностью читает момент
   исчезновения. Кольцо-вспышка в момент НАЧАЛА реакции (`op.start`,
   `_impactAt`) остаётся без изменений — это отдельный, обязательный
   сигнал (см. Часть 2, «момент начала реакции требует отдельного
   сигнала»), не то же самое, что убранное финальное кольцо.
3. **Вриддхи разъединена с elide по count — общий дефолт (200) для неё
   оказался «феерией выстрелов из каждой грани», не читаемой.** Раньше
   вриддхи молча наследовала count через дефолт `spawnSparkleBurst` — с
   ростом дефолта под elide (16→200) вриддхи непреднамеренно раздулась
   вместе с ним, хотя многоточечный разброс по всей грани КРУТЯЩЕГОСЯ
   кубика, повторяемый ~14 раз за оборот (период 280мс), для вриддхи никогда
   не был уместен («плавное ненавязчивое сопровождение», не главный сигнал
   события — им остаётся сам оборот+металлик). Явный `count:15` в вызове
   внутри `applyTransform` (в 10-15 раз меньше нового дефолта, по прямой
   просьбе) — elide и вриддхи больше НЕ делят одно число неявно через
   дефолт, у каждого свой явно заданный вызов. 3 новых теста (цвет искр
   elide, отсутствие финального кольца, count=15 у вриддхи).

**ПЯТАЯ правка той же сессии — направление отстойника для «a» в rule 42,
разобрано и ЗАКРЫТО.** Пользователь предложила: раз e+a→ai — по сути
замена/слияние, а не «простое исчезновение», то «a» стоит поднимать вверх
в отстойник, как e во время `split` в agnayas («e» там — буквально
источник, физически распадающийся на a+y). Встречный довод (принят
пользователем): «ai» — собственная вриддхи-ступень самой e (та же лестница
i→e→ai, что у guṇa, Whitney §127) — «a» лишь nimitta, запускающая сдвиг
соседа, сама не становится частью «ai» и не переживает событие ни в какой
форме (в отличие от split, где источник — буквально материал результата).
По зарезервированному смыслу («вверх = САМА буква продолжается в новой
форме») — вниз остаётся верным.

Но пользователь подняла СЛЕДУЮЩИЙ, более общий вопрос: если направление
не меняется, то ХОТЯ БЫ эффект (искры+сжатие, только что добавленные для
elide) не всегда обоснован — «в 15 и 55 вспышка обоснована, буква просто
выпадает [это и есть правило]; в 42 нужно решить». Сформулирован и
закреплён общий критерий (Часть 4 ниже, две отдельные строки реестра):
**исчезновение — само содержание правила (полный эффект) ИЛИ побочный
спутник ДРУГОГО, уже показанного главного события в том же шаге
(`quiet:true` — без искр, без ускоренного сжатия, линейное угасание на
весь `fadeDur`)?** Rule 42 — второй случай (a — nimitta вриддхи, главное
событие уже показано золотым вращением e→ai), rule 15/55 — первый. Новый
`ElideOp.quiet` булев флаг, вспышка-удар в НАЧАЛЕ реакции не затронута
(отдельный обязательный сигнал в любом случае, не «эффект»). 1 новый тест.

**Отдельно, тем же заходом: пользователь показала скриншот rule 42
(«tatraiti», уже собранное слово) с замечанием «неровно встало».** Прогнан
полный таймлайн реальным кодом до конца — позиция/поворот/масштаб КАЖДОГО
кубика: все X с идеальным шагом SLOT(1.2), все Y=0, все повороты=0, весь
масштаб=1, включая кубик «ai». Численно НИКАКОГО отклонения не найдено —
причина «неровности» на скриншоте НЕ мезh-уровня (не позиция/поворот/
масштаб), скорее всего это про отрисовку самого глифа «ai» на грани
(авто-подгонка шрифта для 2-буквенных диграфов) или про что-то, что
численная проверка структуры данных не покрывает. **Открытый пункт** —
не решено, ждёт более точного описания того, что именно выглядит неровно.

## Часть 4 — Реестр эталонных эффектов (справочник, не источник для
копирования кода вручную)

**Правило пользования:** прежде чем писать `ops` для нового примера —
сверить каждую ситуацию с этой таблицей. Ситуация уже есть — берётся
готовая техника. Ситуации нет — после того как решена для нового примера,
таблица дополняется В ТОТ ЖЕ МОМЕНТ. Эта таблица покрывает только 5 уже
ПОСТРОЕННЫХ правил — для предварительного плана механики любого из
остальных 66 правил сначала смотреть
`docs/reference/interaction-registry.md` (заход 79), только потом сюда
за деталями реализации, если тип ситуации уже встречался.

| Ситуация | Обязательная техника | Где реализовано |
|---|---|---|
| Триггер непрерывно воздействует на цель | Текстурный пульс на триггере (`setFacePulse`/`redrawPulseFace`), НЕ отдельный DOM-слой | `approach.holdPulse` (śādhi), `influence` (agnayas, унифицировано заход 43) |
| Конкретный сигнал долетает от триггера к цели (дискретный пакет) | `spawnWave` | `influence`, `approach.holdPulse` — уже единообразно |
| Буква превращается в другую на месте | `transform`, 4 категории — см. Часть 3 | agnayas, rule 71, taddhiraṇyam |
| Сближение вызывает реакцию у цели | Двухотрезочный `approach` с паузой | śādhi |
| Момент начала реакции | Вспышка+скачок масштаба РОВНО в момент начала, не только в конце | `elide` |
| Буква исчезает без замены, И ЭТО СОДЕРЖАНИЕ ПРАВИЛА (никакого другого главного события в шаге нет) | `elide`, погружение вниз, полная непрозрачность на rise+hold, угасание+россыпь искр СОБСТВЕННОГО цвета буквы (`ringColorFrom(colorFor(tr))`) сосредоточены в fade — драматично, это и есть то, что мы показываем | śādhi (s→∅), rule 55 (s→∅) |
| Буква исчезает без замены, но ПОБОЧНО — спутник другого, уже показанного главного события в ТОМ ЖЕ шаге (nimitta, поглощённая результатом чужой трансформации) | `elide` с `quiet:true` — тот же погружение вниз, но БЕЗ россыпи искр и БЕЗ ускоренного сжатия (линейное угасание на весь `fadeDur`); вспышка-удар в НАЧАЛЕ реакции остаётся (отдельный обязательный сигнал, не декоративный эффект) — яркий эффект здесь конкурировал бы вниманием с уже отыгранной кульминацией | rule 42 (a — nimitta вриддхи, главное событие — золотое вращение e→ai) |
| Одна буква становится двумя | `split`, подъём вверх | agnayas (e→a+y) |
| Две буквы САМОПОДОБНЫ и сливаются в одну (a+a→ā) | `merge`, едущий кубик вдоль ряда | āsīt (a+a→ā) |
| Два РАЗНЫХ звука сливаются в один НОВЫЙ (не самоподобие) | ДВА параллельных `split` (каждый источник поднимается сам, синхронизированы гаснуть одновременно) — `arrivals` только у ОДНОГО из них (пустой массив у второго — законно, не ошибка) | rule 50 (-as→o, devas+asti→devo'sti) |
| Буква не исчезает, а становится ДРУГИМ ВИДИМЫМ символом (не звуком с фонетическим цветом) | `transform`, `signal:'blank'` — `colorFor` для нестандартного глифа падает в нейтральный `COL_DIM` без нового кода | rule 50 (a→аваграха, `toGlyph:"'"`) |
| Морфологическая граница внутри примера | Части разделены с начала, событие — следствие сближения | āsīt, śādhi |
| Внешние сандхи, граница слов не схлопывается | Зазор остаётся навсегда, ничего его не трогает | vāk asti, taddhiraṇyam |
| Длинный пример (>10 фонем) | Сжатые крайние блоки, авто-подгонка шрифта, лимит 3 (искл. 4 для правила 62) | taddhiraṇyam («yam») |

### 5.2 — 3D слот-движок — НОВАЯ, малая по охвату система (эта сессия)

Одиннадцать правил, у каждого полноценная 3D-анимация (не просто подсветка
алфавита) — интегрированы в основное приложение десять (включая rule 1,
подтверждён визуально «ДЕВАУ — нормально»), rule 2 на тестовом полигоне,
ждёт визуальной проверки (последняя, merge-based версия механики).

**НАЙДЕННЫЙ РЕАЛЬНЫЙ КОНФЛИКТ ДВИЖКА (при планировании rule2, поймано
численной симуляцией ДО сдачи, не в браузере): `transform` и `approach` НЕ
компонуются на ОДНОМ кубике одновременно.** Во время активной фазы
вращения `applyTransform` КАЖДЫЙ кадр принудительно пишет `cube.mesh.
position.x = slotX(op.at) + боковое раскачивание` (см. `slot-engine-ops.js`,
блок `if (!op._landed)`) — если на том же кадре ДО этого уже отработал
`applyApproach` и сдвинул кубик физически в сторону, `applyTransform`
следующим же вызовом эту позицию перетирает обратно к исходному слоту.
Обнаружено при попытке буквально одновременно «двигать ī к a и одновременно
крутить его в e» (по прямой первой формулировке плана) — реальный прогон
показал, что кубик застревает в исходном слоте всё время вращения, ничего
физически не приближается. **Верное решение (использовано в rule2, тот же
приём УЖЕ был у agnayas, просто не был явно так сформулирован раньше):
если гунация/вриддхи должна произойти НА том же кубике, который потом ещё
и физически сближается — сначала `transform` ЦЕЛИКОМ, на месте, БЕЗ
approach; approach запускается СТРОГО после `t>=1` (после `op._landed` —
после этого момента `applyTransform` больше НИКОГДА не трогает position.x,
см. код).** НЕ применимо для случаев, когда approach нужен ИМЕННО во время
паузы `midDistance` (там approach управляет позицией, а реакция —
`elide`/`transform` НА ДРУГОМ кубике, не на движущемся — как в śādhi, где
DH подъезжает, а реагирует, исчезая, именно S, другой кубик) — конфликт
возникает ТОЛЬКО когда ОБЕ операции пишут в position.x ОДНОГО И ТОГО ЖЕ
кубика. Стоит иметь в виду при планировании любого будущего правила, где
гунация/вриддхи-транcформация происходит НА кубике, который в том же шаге
ещё и физически сближается с соседом.

**Rule 61 (hasannagacchat) — ПЕРВЫЙ реальный тест гэпа DOUBLE (истинная
геминация).** hasan «смеющийся» + agacchat «шёл» → hasannagacchat «шёл
смеясь»: после краткого простого гласного конечный n удваивается перед
следующим гласным. По прямой поправке пользователя (дважды за сессию):
(1) правило 10 (gacchati, ch→cch) сначала казалось кандидатом, но
отвергнуто — «cch» орфографически c+ch, РАЗНЫЕ буквы (стандартное
правило Уитни о деаспирации первой копии при геминации придыхательных),
это обычный `split`, не тест истинного удвоения; (2) условие правила —
ДВА гласных разом (предшествующий И следующий), оба получили `influence`
на n, не один; (3) механика — НЕ `split` (подъём в отстойник), а НОВАЯ
операция `bud` («отпочкование», см. реестр типов операций выше) — по
прямому образному запросу «как будто капля отрывается от другой капли,
но форма куба должна оставаться основной», зеркало `merge`. Раскладка —
10 из 10 слотов, сжатые блоки ТОЛЬКО на самом краю (`has`/`at`, по 1
блоку с каждой стороны, не два подряд — прямое уточнение методологии
сжатия). Отдельного финального `approach` не нужно — целевой слот клона
это и есть внешний зазор между словами, закрывается самим событием
геминации, без дополнительного шага (упрощение относительно rule50/

   же самая настройка (0.22) на ДРУГИХ буквах даёт идеальную прозрачность

   фоне»), а в баге, который проявляется через раз, по кубику, а не

   НАРОЧНО, по просьбе пользователя, для будущего расследования — не
   убирать не разобравшись. Тестировать ТОЛЬКО во время активного окна
   притенения (не после `settle` — там `frame()` каждый кадр принудительно
   возвращает всем `opacity:1`, любая ручная правка через консоль
   мгновенно затирается на следующем кадре, тест ничего не покажет).

    ступени). Вскрылось на прямой вопрос пользователя «что значат цветные
    квадратики» — точки на карточках `docs/index.html` (раздел 02) без
    легенды на странице объяснить было нечем, а сама легенда изнутри
    противоречила себе. **Исправлено:** `--c-weak` закреплён СТРОГО за
    сампрасараной; аваграха переведена на `--c-ending` (граница/окончание
    морфемы — смысловая семья ей ближе). Заодно найдено и исправлено:

    то `--c-new` вперемешку, хотя при простом исчезновении звука НИЧЕГО
    нового не образуется — новый общий приём: `--c-stem` с `opacity:.42`

    теряющий существование», перенесено из исходной идеи effects-map.html,
    где lopa уже была прозрачным `c-stem`, просто это не было перенесено
    на карточки при первой сборке `index.html`). Ассимиляция (rule70/71)
    ошибочно красилась в `--c-new` («новый сегмент») — заменено на
    `--c-ending`, т.к. ничего нового физически не возникает, меняется
    только звонкость/место уже существующего согласного. Видимая
    компактная легенда (`.dot-legend`) добавлена перед сеткой раздела 02,
    полная — в самом разделе 04. Единая, теперь непротиворечивая таблица
    цветов: зелёный = согласный/основа, обесцвеченный зелёный = выпадение,
    серебро = гуна, золото = вриддхи, охристый (`--c-weak`) = слабая
    ступень СТРОГО, бирюза = новый сегмент, горчичный (`--c-ending`) =
    граница/окончание/аваграха, терракота (`--c-trigger`) = внешний
    триггер-катализатор.

## Часть 7 — Как построить новый пример (методология)

0. **Сверить формулировку правила с Уитни и найти точный номер сутры
   Панини, ПРЕЖДЕ чем писать Поток А.** Прямое требование (найдено при
   rule1/rule10 — короткая формулировка Эменó несколько раз оказывалась
   односторонней/неполной без этой сверки, а `interaction-registry.md`
   `effects-map.html` заранее — по сутрам Панини — предсказывали
   механики, которые иначе пришлось бы изобретать заново). Не отдельный
   аудит по всем 71 правилам разом (сознательно отклонено пользователем
   как слишком крупный, непроверяемый объём за один присест) — а
   обязательный шаг ВНУТРИ построения КАЖДОГО отдельного примера, по
   порядку автопостройки. Порядок источников при неясности — Часть 2а.
   Сутра Панини (не только Уитни-номер) идёт в комментарии данных, в
   `roleDemo.text` (см. п.8а ниже) и в реестр (`interaction-registry.md`).
1. Заполнить **Поток А** — грамматический разбор правила без оглядки на
   технику: пронумерованные события, что происходит и почему. Каждое
   грамматическое/сандхи-событие — отдельная строка.
2. Для каждого события Потока А сверить с **реестром (Часть 4)** — если
   подходящая техника уже есть, использовать её. Если нет — это пункт в
   гэпах (Часть 6): сначала решить, добавляется ли новый `op`-тип в
   движок или комбинация существующих, и только потом писать данные.
3. Прежде чем писать `initial`/`ops` — явно ответить на вопрос **Главного
   принципа (Часть 2)**: где граница, что физически происходит при
   контакте?
4. Проверить **зарезервированные значения (Часть 3)**: категория
   transform (какой угол/сигнал), направление раскачивания, лимит на
   сжатые блоки, цвет вспомогательных шагов.
5. Только когда каждая строка Потока А имеет пару в технике (или
   осознанно оставлена «данными, не движком») — переходить к числам
   таймлайна. Считать формулами (падение → буфер → длительность операции
   → следующий буфер), не подбирать на глаз.
6. Прогнать **численную симуляцию реального кода** (вырезанного из
   файла) на всём таймлайне — не только на happy path, включая моменты,
   где цель/сосед могут исчезнуть или пересечься.
7. Собрать тестовую страницу (`test-slot-engine-ruleN.html`), добавить
   ссылку в секцию «Слот-движок · в работе» на `docs/index.html` (секция
   заводится заново, если её сейчас нет — см. Часть 6, гэп 11, держится
   пустой не по умолчанию). Ждать визуальной проверки пользователем —
   численная проверка НЕ равна визуальной готовности.
8. После подтверждения — интегрировать в `EXAMPLES[N]`, переписать текст
   пояснения под академический регистр (Часть 1, п.3).
8а. **`roleDemo.text` обязательно называет части речи и грамматические
   категории (Часть 1, п.3а), не только фонетический механизм** — часть
   речи, род/число/падеж, тип основы и т.п. для каждого задействованного
   слова/морфемы, плюс сутра Панини из шага 0.

## Приложение — agnayas (правило 3) целиком, как образец применения
методологии выше

Формула: **agni + as → agnaye (гуна) → agnayas (правило 3)**.

| # | Что происходит | Разряд |
|---|---|---|
| A0 | Исходная форма: `agni` + `as` | — |
| A1 | Окончание `-as` требует гунации предшествующей i-основы | [Грамм.], не сандхи (Whitney §338a) |
| A2 | `i → e` (гунация) | [Грамм.] |
| A3 | Промежуточная форма `agne`+`as` — несовместимое сочетание гласных на стыке | — |
| A4 | Правило 3: `e + a → a + y + a` | [Сандхи 3] |
| A5 | Итог: `agnayas` | — |

A1–A2 (гунация) и A4 (правило 3) — ДВА разных, независимых события с
разными причинами → два отдельных `step` с независимыми `activeSlots`,
не один растянутый шаг.

**Слоты:** 1=a, 2=g, 3=n, 4=i→e, 5=(пусто, под будущий Y), 6=a, 7=s.

**Таймлайн (мс):**

| мс | Событие |
|---|---|
| 0–2600 | Падение всех 6 букв |
| 2600–6700 | Шаг «грам.»: `influence` от {a,s} к i, `transform` i→e (серебро→серебро→истинный цвет) |
| 6700–8300 | Пауза-проявление (авто) |
| 8300–16150 | Шаг «правило 3»: `approach` (несовместимость, отскок) → `split` (пауза-осознание → подъём E → прилёт A+Y по дуге → сравнение → исчезание E) |
| 16150–17630 | Хвостовая пауза-проявление (авто) |
| 18630–20310 | `settle` (авто-старт = конец проявления + 1с) |

Точные параметры каждой операции — в `docs/app/examples/rule3-agnayas-slots.js`.
