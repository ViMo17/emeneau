# Тесты

Настоящие, постоянные тесты — не одноразовые проверки в чате. Запускаются
локально через встроенный тестраннер Node (без внешних зависимостей типа
Jest/Vitest — тот же принцип минимализма, что и во всём проекте).

## Запуск

```bash
npm install   # один раз — ставит three и jsdom как dev-зависимости (см. ниже)
npm test
```

## Что покрыто сейчас

Каждый файл тестов привязан к КОНКРЕТНОЙ, реально пойманной ошибке — не
абстрактным «на всякий случай». Все 10 обработчиков операций слот-движка
(`applyTransform`, `applyElide`, `applyInfluence`, `applyApproach`,
`applySplit`, `applyMerge`, `applyArrive`, `applySettle`, `applyDim`,
`applyStepDim`) — на уровне модуля, каждый со своим тестовым файлом
(`tests/applyX.test.mjs`) и общим контекстом `ctx` вместо захвата
состояния через замыкание. Кроме них:

- `colorFor.test.mjs` — придыхательные согласные (kh/gh/.../dh) и дифтонги
  ai/au не должны получать нейтральный цвет сжатого блока.
- `buildRuntimeSteps.test.mjs` — проявление между шагами цепочки правил с
  одинаковым составом участников не должно вставляться вообще (иначе
  волна проявления обрывается на середине при короткой паузе и широкой
  раскладке — асимметрия прозрачности у одной и той же буквы в двух
  позициях ряда).
- `transformKind.test.mjs` — категории `transform` (парная замена внутри
  варги / общая ассимиляция под соседа) дают ТОЧНО те `spinTurns`/`signal`,
  что задуманы — раньше угол поворота путали при ручном повторении чисел.
- `validateExampleData.test.mjs` — данные нового примера с опечаткой в
  обязательном поле (`toGlyph`/`at`/`delay` и т.п.) ловятся при загрузке
  с понятной ошибкой, не тихим `NaN`/`undefined` где-то в кадровом цикле.
- `moduleBarrel.test.mjs`, `cubeUnification.test.mjs`, `dataModule.test.mjs`
  — целостность барабан-файла `slot-engine.js`, общая геометрия/материалы
  кубика, форма и непротиворечивость данных `data.js`.

Слой UI-разметки приложения (`docs/app/alpha-panel.js`, `rule-panel.js`,
`role-demo.js` — панель алфавита, карточки правил, 2D-подсветка ролей)
покрыт через jsdom (`tests/helpers/domStub.mjs` — точная копия id/классов
из `sanskrit-sandhi-app.html`; см. «Про jsdom» ниже):

- `alphaPanel.test.mjs` — рендер `ALPHA_ROWS`, пин буквы, тултип,
  аудио-заглушка, снятие пина кликом по фону (`document`-слушатель).
- `roleDemo.test.mjs` — подсветка ролей источник/триггер/результат,
  лента кнопок шагов, синхронизация с 3D через событие `slotstep` и
  снятие слушателя в `clearRoleDemo` (иначе слушатели копятся на каждый
  новый пример), подсветка столбца таблицы гуна/вриддхи через
  `MutationObserver`.
- `rulePanel.test.mjs` — рендер карточек по `SECTIONS`, склейка примера
  из `EXAMPLES[n]` со вторым примером из текста правила (см. `showCenter`),
  плейсхолдеры «примеры/упражнения не добавлены», переключение пина между
  карточками, диапазон правил 17–29. Реально пойманная тестами на
  написании ошибка (не гипотетическая): правило 39 даёт из `emeno` ДВА
  примера через «;», первый совпадает с `EXAMPLES[39][0].desc` дословно
  (интерактивный чип), второй — нет (законный отдельный чип, не дубликат
  и не баг) — было бы легко ошибочно «исправить» код под неверное
  предположение «ровно один чип», если бы это не проверялось явно.

## Известное ограничение — что НЕ покрыто и почему

Клик по примеру С 3D-модулем (agnayas/āsīt/śādhi — `EXAMPLES[3]`/`[7]`/
`[15]`) не тестируется: `mountAnimExample()` делает реальный
`await import()` слот-движка, который создаёт THREE.js-сцену и просит у
canvas WebGL-контекст — jsdom его не даёт. Сама 3D-анимация (тайминги,
геометрия) по-прежнему проверяется численной симуляцией, а не автотестом
(см. CLAUDE.md, Часть 1 п.6) — там нет браузера вообще, только Node.js.

Также `role-demo.js`: jsdom не считает раскладку (`getBoundingClientRect()`
всегда возвращает нули) — линии источник→результат на алфавите
(`svgRoleLine`) поэтому в тестах никогда не рисуются (код всегда попадает
в ветку «клетки слишком близко, линия не нужна»). Классы ролей и текст
шага это не проверяет — тестируется отдельно, сами линии — только
визуально в браузере.

## Про версию `three` в devDependencies

Реальная версия в браузере — r128, вендорена локально
(`docs/app/vendor/three.module.js`), НЕ через npm. Пакет из
`node_modules` нужен только чтобы `import * as THREE from 'three'`
резолвился при запуске тестов в Node — протестированные здесь функции
(`colorFor`, `buildRuntimeSteps` и т.п.) сами THREE.* не вызывают, так что
версия сейчас тестам не мешает в любом случае. Тем не менее версия в
`package.json` зафиксирована ТОЧНО на `0.128.0` (без `^`), а не оставлена
на широком диапазоне — если код, который реально использует THREE (сцена,
геометрия, `mountSlotExample`), когда-нибудь окажется на уровне модуля и
получит тесты, расхождение версий стало бы реальным источником ложных
провалов/пропусков.

## Про jsdom

Нужен только для тестов UI-слоя (`alphaPanel`/`roleDemo`/`rulePanel.test.mjs`)
— в браузере движок работает с настоящим DOM, jsdom в продакшн не попадает.
`tests/helpers/domStub.mjs` устанавливает `globalThis.document`/`window` ДО
импорта тестируемого модуля — обязательно динамическим `await import()`,
не статическим: статический `import` хостится и выполнился бы раньше
любого кода в тестовом файле, включая вызов `installDomStub()`, — модуль
успел бы вызвать `document.getElementById(...)` на ещё не установленном
`document` и упасть на первой же строке.
